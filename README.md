# ChronoLux

**Time, Engineered for You.** ChronoLux is a full-stack watch storefront starter for smart, luxury, analog, digital, sports, casual, automatic, mechanical, chronograph, couple, men's, women's and kids' watches.

This repository includes a responsive storefront, PostgreSQL-backed commerce APIs, Auth.js email/password accounts, customer and admin areas, Stripe Checkout integration, and a development-only test payment mode. Product and contact data are stored in PostgreSQL. Demo watch artwork is included as local SVG assets so the seeded catalog does not rely on fragile third-party image URLs.

> Before accepting live orders, replace the sample contact details and demo product data, set your real tax/shipping policy, configure a production email sender and payment gateway, review returns/warranty terms, and complete the production checklist below.

## Technology stack

- Next.js App Router, React, TypeScript, Tailwind CSS 4, and Framer Motion
- PostgreSQL with Prisma 7 and the `@prisma/adapter-pg` Node PostgreSQL driver adapter
- Auth.js credentials provider, JWT sessions, bcrypt password hashing, and database-backed role checks
- Zod server validation, Stripe-hosted Checkout, Resend password-recovery email, Vercel Blob image uploads
- Lucide icons; local SVG watch illustrations; responsive CSS and server-rendered catalog/detail pages
- Vercel-compatible Node.js runtime and Prisma client generation during install/build

## Features

- Premium responsive home page, catalog, category pages, product detail galleries, features/specifications guides, reviews and contact pages
- Product search and suggestions; category, brand, price, gender, type, material, display, water-resistance, rating and stock filters; sorting and pagination
- 20 seeded demo watches, 13 categories and 6 demo brands; product ratings and reviews are recalculated from published reviews
- Email/password signup, login, logout, profile/password management, forgot/reset-password flow, and admin promotion from a trusted CLI
- Guest cart in local storage, signed-in database cart, cart merge after login, saved wishlist and addresses
- Server-calculated INR order totals, transactional inventory reservation, order snapshots, development test orders, Stripe Checkout redirects, signed webhooks and stock release after payment-session expiry/failure
- Verified-purchase reviews with edit/delete, reporting, moderation, rating distribution and sorting
- Admin dashboard and role-protected APIs for catalog/inventory, categories, brands, orders, customers, reviews, contact messages, product image upload and sales summaries
- Contact messages and newsletter subscriptions persist in PostgreSQL
- Metadata, Open Graph defaults, product structured data, sitemap and robots rules
- Accessible loading, empty and error states, toasts, mobile navigation, keyboard labels and responsive layouts

## Database architecture

`prisma/schema.prisma` is the source of truth. A checked-in PostgreSQL initial migration lives in `prisma/migrations/`.

| Area | Models | Notes |
| --- | --- | --- |
| Identity | `User`, `PasswordResetToken` | Unique email, role, password hash, active flag, expiring hashed reset tokens |
| Catalog | `Product`, `Category`, `Brand`, `ProductImage` | Product type/gender enums, inventory, Decimal money, JSON specs, array features/tags/options, indexed filters |
| Customer | `Address`, `Cart`, `CartItem`, `Wishlist`, `WishlistItem` | Per-user cart and wishlist, address ownership, unique product entries |
| Commerce | `Order`, `OrderItem` | Immutable address and product snapshots, totals, payment/order states, inventory references |
| Trust/support | `Review`, `ReviewReport`, `ContactMessage`, `NewsletterSubscriber` | Unique user/product review and report constraints, moderation status, persisted messages/subscriptions |

Orders retain product name, slug, image, variant, quantity and price snapshots so order history remains readable when a catalog entry changes or is archived. Passwords are bcrypt hashes; reset tokens are stored only as SHA-256 hashes. Do not add secrets to this schema or seed data.

## Install and configure locally

From this project directory:

```powershell
npm install
Copy-Item .env.example .env
```

Open `.env` and set `DATABASE_URL` to a reachable PostgreSQL database. Generate a unique Auth.js secret with:

```powershell
npx auth secret
```

Put the generated value in `AUTH_SECRET`. Do not commit `.env`. The Prisma client is generated by `npm install` and again by the production build.

For a local PostgreSQL installation, create an empty database named `chronolux` and set its actual username, password, host and port in `.env`. If your provider uses a pooled runtime connection, set `DATABASE_URL` to the pooled URL and optionally set `DIRECT_DATABASE_URL` to its direct/unpooled URL for migrations. Locally, both may point to the same database URL.

## Environment variables

| Variable | Required | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | Yes | PostgreSQL runtime URL; use SSL and your provider's pooler where appropriate for serverless |
| `DIRECT_DATABASE_URL` | Optional | Direct/unpooled PostgreSQL URL for Prisma migrations; takes precedence in `prisma.config.ts` |
| `AUTH_SECRET` | Yes | Auth.js signing/encryption secret; generate with `npx auth secret` |
| `AUTH_URL` | Local/optional in Vercel | Auth.js canonical origin; local default is `http://localhost:3000` |
| `PAYMENT_MODE` | Optional | Set `mock` only for local development; omit or set `stripe` for real checkout |
| `STRIPE_SECRET_KEY` | For live payments | Server-only Stripe key used to create hosted Checkout sessions |
| `STRIPE_WEBHOOK_SECRET` | For live payments | Server-only secret used to verify Stripe webhook signatures |
| `RESEND_API_KEY`, `EMAIL_FROM` | Optional; required for reset email | Sends password-reset links; without these, requests receive a generic response but no email is sent |
| `BLOB_READ_WRITE_TOKEN` | Optional | Enables admin image uploads to Vercel Blob; local assets and configured Blob URLs are also accepted |
| `NEXT_PUBLIC_SITE_URL` | Production | Public canonical origin used for metadata, password-reset URLs, sitemap and Stripe return URLs |
| `NEXT_PUBLIC_STORE_TAX_RATE` | Optional | Decimal tax rate, default `0.18` (18%); confirm the actual rate and tax rules for your business |
| `NEXT_PUBLIC_FREE_SHIPPING_THRESHOLD` | Optional | INR order subtotal for free shipping, default `10000` |
| `NEXT_PUBLIC_STANDARD_SHIPPING_FEE` | Optional | Standard shipping charge in INR, default `399` |
| `NEXT_PUBLIC_INSTAGRAM_URL`, `NEXT_PUBLIC_FACEBOOK_URL`, `NEXT_PUBLIC_YOUTUBE_URL` | Optional | Full profile URLs shown only when configured |

Stripe Checkout redirects to Stripe-hosted payment pages, so a publishable browser key is not needed by this implementation. Private keys must never use a `NEXT_PUBLIC_` prefix.

The seed operation upserts its demo categories, brands and 20 products, so it can be rerun. It includes fictional demo brands and locally hosted vector illustrations. Replace these with your catalog and licensed photography before launch.

Useful database commands:

Use `db:migrate` while developing schema changes; commit the resulting migration. Use `db:deploy` to apply committed migrations to staging/production. Prisma migrations use `DIRECT_DATABASE_URL` when it is set.

```powershell

```

Open `http://localhost:3000`. Production checks and serving commands:

```powershell

```

When `PAYMENT_MODE=mock` and `NODE_ENV` is not `production`, checkout creates orders marked `TEST_PAID`; the interface states that no payment was collected. This mode is rejected in production. ## Create the first admin account

1. Start the app and create an account using the signup page.
2. Promote that exact email using a trusted terminal connected to the intended database:

```powershell
npm run admin:promote -- owner@example.com
```

Replace `owner@example.com` with the account email you created. The command changes only the role of an existing account. Keep the database URL private and promote only a trusted owner. Admin pages and admin APIs check the current database role on the server.

## Payment, email and image services

### Stripe

Set `PAYMENT_MODE=stripe`, `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`. In your Stripe dashboard, register the endpoint `https://YOUR_DOMAIN/api/payments/stripe/webhook` and subscribe to `checkout.session.completed`, `checkout.session.expired`, and `checkout.session.async_payment_failed`. Copy the endpoint signing secret into `STRIPE_WEBHOOK_SECRET`. Test a complete payment and webhook round trip in Stripe's test mode before switching to live keys. The app never marks a Stripe order paid based on the browser return URL.

### Password reset email

Configure a verified sender and `RESEND_API_KEY` plus `EMAIL_FROM`. The forgot-password API intentionally returns the same message for existing and unknown email addresses. The one-time reset token expires after one hour and is stored as a hash. Configure and test email delivery before relying on account recovery.

### Product images

Configure the Vercel Blob integration and `BLOB_READ_WRITE_TOKEN` to upload JPG, PNG, WebP or AVIF files (up to 5 MB) in the admin product editor. The seed artwork is local SVG. Uploaded images use Blob-hosted URLs. Without a token, admins can use local `/...` assets already inside `public/`; image URLs are restricted to local paths or Vercel Blob URLs supported by the Next.js image configuration.

## Deploy to Vercel

1. Push the project to GitHub using the commands above.
2. In Vercel, import the repository and keep the detected Next.js build settings. The build runs `prisma generate && next build`.
3. Create a PostgreSQL database with your chosen cloud provider. Set `DATABASE_URL` to its SSL-enabled pooled/runtime URL if the provider recommends a pooler. Set `DIRECT_DATABASE_URL` to the direct/unpooled URL for migrations when available.
4. Add `AUTH_SECRET`, `AUTH_URL` (your production origin if required), `NEXT_PUBLIC_SITE_URL`, tax/shipping values and payment/email/blob variables in Vercel Project Settings. Add production variables to the Production environment and separate test credentials to Preview as appropriate. Never put private secrets in `NEXT_PUBLIC_*` variables.
5. Before the first deployment, apply migrations from a trusted machine or CI job with the production database variables loaded:

   ```bash
   npm ci
   npm run db:deploy
   ```

   Run `npm run db:seed` only if you intend to load the demo catalog into that database. Do not seed a live store with demo inventory unintentionally.
6. Deploy from Vercel. Subsequent schema changes should be committed as migrations and applied with `npm run db:deploy` before or as part of the release process.
7. Promote the initial owner account with `npm run admin:promote -- owner@example.com` in a trusted shell pointed at production. Use a protected CI/local environment and do not paste database credentials into GitHub.
8. Configure the production Stripe webhook URL and signing secret, email sender, Blob token, real business contact details, legal policies and actual tax/shipping settings.
9. Test signup, login, search/filter, product/cart/wishlist, payment/webhook, order history, verified reviews, contact/newsletter, admin inventory/order actions, reset email, sitemap and mobile layouts on the deployed domain.

Vercel does not provide a local persistent disk for product uploads or database storage; the application uses PostgreSQL and optional Blob storage instead. `DIRECT_DATABASE_URL` is used by Prisma migration commands while `DATABASE_URL` is used by the application adapter.

## API overview

| Route | Methods | Access |
| --- | --- | --- |
| `/api/products`, `/api/products/[slug]`, `/api/categories`, `/api/search` | GET | Public active catalog |
| `/api/auth/signup`, `/api/auth/forgot-password`, `/api/auth/reset-password`, `/api/auth/[...nextauth]` | POST/GET | Signup/recovery/Auth.js |
| `/api/cart`, `/api/wishlist` | GET/POST/PUT/DELETE | Authenticated; guest cart stays local until merge |
| `/api/addresses`, `/api/addresses/[id]`, `/api/account`, `/api/account/password` | GET/POST/PATCH/DELETE | Authenticated owner |
| `/api/checkout`, `/api/orders`, `/api/orders/[id]` | POST/GET | Authenticated owner |
| `/api/reviews`, `/api/reviews/[id]`, `/api/reviews/[id]/report` | GET/POST/PUT/DELETE | Public read; verified owner write; signed-in report |
| `/api/contact`, `/api/newsletter` | POST | Public validated submission |
| `/api/payments/stripe/webhook` | POST | Stripe signature required |
| `/api/admin/*` | GET/POST/PUT/PATCH/DELETE | Database-verified admin only |

All request bodies are validated server-side. Product list filters are query parameters (including `category`, `brand`, `type`, `gender`, `minPrice`, `maxPrice`, `strap`, `case`, `display`, `water`, `rating`, `availability`, `sort`, `page`, `limit` and `q`).

## Manual verification checklist

With PostgreSQL running, `.env` configured, migrations applied and the seed loaded:

1. Open the home page at desktop, tablet and mobile widths; test navigation and category links.
2. Sign up, log in, log out, reset a password through configured email, and edit the profile/password.
3. Search a product by name/model/brand; combine catalog filters, sorting and pagination.
4. Open a product, use gallery/color/strap/quantity controls, add to wishlist, and add/remove/update cart lines.
5. Sign in after creating a guest cart and confirm items merge into the database cart.
6. With local `PAYMENT_MODE=mock`, place a test order and confirm the UI and order record identify it as a no-payment development order.
7. With Stripe test keys/webhook, complete a test checkout and confirm the order remains pending until a valid webhook arrives; test expiry/failure stock release.
8. Confirm users see only their own order details, addresses and wishlist.
9. Submit/edit/delete/report a review; verify non-buyers cannot review and purchased users can.
10. Submit a contact message and newsletter signup; confirm both are in the admin views/database.
11. Promote a test admin; create/edit/archive a product, upload a product image, manage taxonomy, view customers/reviews/messages and update a test order.
12. Verify production build, sitemap, robots rules, product metadata, mobile checkout and Vercel logs.

Automated project checks: `npm run lint`, `npm run typecheck`, `npm run build`, `npm audit`.

## Common issues

- **Prisma cannot connect:** check that the database is running, the URL has the right credentials/database name, SSL parameters match the provider, and outbound connections are allowed. Use `DIRECT_DATABASE_URL` for migrations if the pooled URL cannot run DDL.
- **Missing Prisma Client:** run `npm run db:generate`; `npm install` and `npm run build` also run generation.
- **No watches shown:** run `npm run db:deploy` and `npm run db:seed`, then refresh. Confirm the seeded products remain `isActive`.
- **Signup succeeds but login fails:** check database connectivity, email normalization, and that the account is active. Reset-password email requires Resend configuration.
- **Admin page redirects:** create an account, then run the promote command against the same database used by the app; verify the email exactly.
- **Checkout is disabled:** configure Stripe keys and `PAYMENT_MODE=stripe`, or use the development-only `PAYMENT_MODE=mock` outside production.
- **Order stays pending:** Stripe confirmation comes from the signed webhook. Check the configured webhook URL, event subscriptions, signing secret and Vercel function logs.
- **Image host error:** use an image in `public/` or upload to Vercel Blob. Other remote image hosts must be intentionally configured in `next.config.ts` and the product validation policy before use.
- **Vercel database connection limits:** use a provider-recommended pooler for runtime and keep the application pool small; use a direct connection for Prisma migrations.
- **Build fails on missing auth secret:** generate `AUTH_SECRET` and set it in the relevant local/Vercel environment.

## Production notes

The project supplies commerce workflows and secure integration points, not legal, tax, accounting or fulfillment policy. The contact details, product content, brands, inventory, price/tax/shipping defaults, delivery/return promises and warranty text are sample storefront configuration. Verify them for your business. Stripe refunds, shipment carrier integrations, inventory purchasing and customer-support operations should be added with your chosen providers before those workflows are offered to customers.
